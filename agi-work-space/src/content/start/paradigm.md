这篇介绍 **AGI-WorkSpace 这份工作空间本身**，不是当前业务项目的 PRD。换到真实项目后仍建议保留，方便新成员和 Agent 理解：知识写在哪、谁能改、Vue 做什么、这套范式好在哪、差在哪。

操作步骤见 [WorkSpace 指南](/start/guide)。当前项目是什么见 [项目介绍文档](/start/project-intro)。

## 什么是 Workspace 新范式

**Workspace 新范式**指：把项目当作一个「可执行的知识工作空间」，而不是「一堆页面」或「一套后台 CMS」。

它有四层意思：

1. **事实在仓库里。** 范围、角色、接口、用例、决策都是 Git 里的 Markdown，路径稳定，可 diff、可审、可回滚。
2. **壳与知识分离。** Vue 只提供导航、搜索、预览编辑、按角色写回。加一篇知识 = 加一个 `.md`，不要加一个路由组件。
3. **角色即目录。** 谁能改哪一类文档，由七个锁定的角色 ID 决定，而不是再做账号系统和 CMS 字段。
4. **人与 Agent 同源。** 成员在浏览器里改的，和 Agent 在仓库里读的是同一棵 `src/content/`。Agent 另有一份硬约束：[AGENTS.md](/space/harness/AGENTS)。

一句话：**上下文不进聊天，进仓库；页面不按文档拆，按 Markdown 渲染。**

## 要解决的问题

传统做法里，项目知识会同时出现在这些地方：

- 聊天和会议纪要（不可检索、不可归属）
- 各工具里的「最终稿」（设计、表格、工单，链接会失效）
- Wiki / CMS（和代码仓库两套生命周期）
- 为每一篇文档单独写的前端页面（改文案要发版）

结果是：换人、换 Agent、换迭代时，没有单一事实来源。本范式用「仓库里的角色文档树」把这件事收拢。

## 范式怎么运转

```text
人在浏览器勾选角色
        ↓
读 / 改 Markdown 预览
        ↓
有权限则写回 src/content（图片进 assets/）
        ↓
绑定代码空间后 commit / push
        ↓
Agent 读同一棵树 + AGENTS.md 再改代码或文档
```

空间配置（配置中心、项目引用、Harness）单独一组，不和「项目总览 / 产品设计 / 研发设计」混在同一棵文档树里，避免把运行配置当成业务需求。

## 和常见方案对比

| 维度 | 常见文档站 / CMS | 一页一 Vue | 本 Workspace |
| --- | --- | --- | --- |
| 知识存在哪 | 数据库或外链 Wiki | 组件和文案混在前端 | `src/content/**/*.md` |
| 加一篇文档 | 后台新建条目 | 加路由、加 `.vue` | 加 `.md`（新分类再加文件夹） |
| 权限 | 账号、角色后台 | 通常没有文档级权限 | 七角色勾选，可写范围是并集 |
| 和代码的关系 | 两套仓库或同步任务 | 文案发版才生效 | 同一 Git 历史 |
| Agent | 靠粘贴或另做 RAG | 很难稳定引用路径 | 读文件 + `AGENTS.md` |
| 不会 Markdown 的人 | 后台富文本 | 找前端改 | 预览里直接改，保存写回 |

## 三条原则

1. **MD-first：** 加知识 = 加 `.md`。新分类 = 文件夹 + `index.md`。禁止为单篇文档增加 `views/*.vue`。
2. **角色即目录：** 角色 ID 锁在 `src/lib/roles.ts`。换项目只换对接人和正文。不要新增第八个角色，除非明确要求并改配置中心与角色表。
3. **空间配置单独一组：** `src/content/space/` 不进左侧「文档目录」树。[开始阅读](/start) 任意已选角色可读可改；其它分类按角色切开。

## 优点

| 优点 | 说明 |
| --- | --- |
| 单一事实来源 | 范围、契约、用例、决策都在可路径定位的文件里 |
| 和 Git 同生命周期 | 评审、blame、回滚、分支试验都跟代码一样 |
| 对 Agent 友好 | 稳定 slug、目录约定、根目录约束文件，不必先爬站 |
| 改知识不必发版 | 保存即写盘；静态托管时随仓库发布即可 |
| 权限足够简单 | 七角色并集，本机勾选，适合小团队模板，而不是平台产品 |
| 不会写 MD 也能贡献 | 预览编辑、表格、贴图 |
| 换项目成本低 | 改 Markdown 和 AGENTS.md 第 1 节表格，不改角色 ID |

## 缺点与边界

| 缺点 / 限制 | 说明 | 怎么面对 |
| --- | --- | --- |
| 不是多人实时协作 | 没有 OT/CRDT、没有在线光标 | 用 Git 分支或错开保存；冲突在 Git 里解 |
| 没有账号体系 | 角色存在本机浏览器 | 适合可信小团队；不要当公网 CMS |
| 写回依赖 Chrome / Edge | File System Access | 只读可用其它浏览器；写盘按指南授权 |
| 现阶段不能在应用里 pull | 只提交推送 | 用 Git 客户端或 IDE 拉代码 |
| 目录纪律要人守 | 乱建分类会把侧栏打乱 | 新分类必须有 `index.md` 和 order |
| 大二进制不适合进 MD 树 | 视频、设计源文件 | 外链设计工具，仓库只放交付说明和导出 |
| 权限不是保密级别 | 未授权角色仍可读其它文档 | 机密不要放进这个工作空间 |

这些不是「以后一定做成 CMS」的借口，而是范式的边界：要的是**可 Git 的项目上下文**，不是 All-in-one 办公套件。

## 适用与不适用

**适用：**

- 需要人、代码、Agent 共享同一份项目事实的研发项目
- 希望换人、换迭代时仍能按目录找到「现在什么是真的」
- 团队能接受 Git，不需要公网多租户

**不适用：**

- 需要对外账号、评论、运营 CMS
- 需要实时共编同一段落
- 知识必须对部分成员保密到「看不见文件」的程度（本模版默认其它目录仍可读）

## 七个角色怎么切开

| 分类 | 放什么 | 不放什么 |
| --- | --- | --- |
| [项目总览](/project) | 概述、目标、角色、状态 | 具体 PRD 字段 |
| [产品设计](/product) | 定义、用户、需求、原型排期 | 测试步骤、实现细节 |
| [体验设计](/design) | 原则、规范、交付清单 | 实现细节 |
| [研发设计](/engineering) | 架构、契约、领域、规范、前端结构 | 发布步骤（归交付运维） |
| [质量保障](/quality) | 计划、用例、证据、缺陷 | 产品范围变更（归产品设计 + 决策） |
| [交付运维](/delivery) | 运维发布、项目计划 | 架构决策正文（归研发设计 / 过程记录） |
| [过程记录](/records) | 已做成的决定 | 进行中的讨论草稿 |

交叉处靠 slug 绑定，而不是再造 CMS 字段。对照表见 [项目角色](/project/roles)。

## 反模式（不要这样做）

- 为「关于我们」「帮助中心」各做一个 Vue 页
- 把结论只发在群里，不写 [项目决策](/records/decisions)
- 改写回或 Git 推送只改代码，不改 [接口契约](/engineering/contracts)
- 把 `space/` 混进文档树，或把业务 PRD 写进 AGENTS.md
- 新增第八个角色却不改 `roles.ts`、配置中心和角色表

## 换项目时动什么

- 改 [项目介绍文档](/start/project-intro)、首页名称与 slogan、[项目概述](/project/overview)、目标、状态、角色对接人
- 改 AGENTS.md 第 1 节表格
- **不要**改角色 ID，不要把 Vue 拆成「一页一文档」，不要用 CMS 换掉 `src/content/`
